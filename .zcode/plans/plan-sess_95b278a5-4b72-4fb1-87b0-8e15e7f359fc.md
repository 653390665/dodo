# InkFlow 墨影 产品体验与链路顺畅度审计（横纵分析法）

目标：以真实运行的方式走通产品全链路，产出一份"功能地图 + 链路顺畅度 + 断点清单 + 改进优先级"的审计报告（Markdown + PDF，风格延续昨天的横纵分析报告）。

## 审计方法

### 1. 链路图谱还原（静态）
- 从 tests/e2e/core-flow.spec.ts、full-browser-click-journey.spec.ts、README 工作流图、plans/ 审计记录反推"设计上的核心用户旅程"：首启向导 → BYOK 配置 → 建书 → 世界观/设定 → 大纲 → 章节生成（治理候选）→ 去AI味审校 → 导出。
- 从 plans/ 里未 DONE 的计划和 release-readiness 的"暂缓项"整理已知薄弱点。

### 2. 实测走查（动态，审计主体）
以"新作者第一次使用"视角实际运行产品（npm run dev），逐链路记录：
- 首启体验：空状态、向导是否能把人带到"能生成"的最短路径
- BYOK 配置：方案A(Gemini)/OpenAI 兼容渠道的实际可用性、报错表现
- 核心创作链：建书 → 设定记忆 → 章节生成（治理候选流）→ 审校预览 → 保存/导出，每步记录：能否走通、等待表现、失败时的降级提示
- 辅助链：能力商店/拆书工厂、记忆雷达、质量体检中心、ContinuationPackView
- 交叉验证：server 日志 + 浏览器 console 的报错与 UI 表现是否一致（报错是否被吞）

### 3. 体验评估基准
用昨天竞品调研的基准衡量：Sudowrite/NovelCrafter 的"最短可用路径"、设定记忆自动追踪、生成等待体验。

### 4. 产出
- 断点清单（每条：位置、现象、严重度、修复建议）
- 链路顺畅度评分（各链路 1-5 分）
- 功能完成度地图（对照 README 宣称 vs 实测）
- PDF 报告交付到工作目录

## 执行顺序
1. 静态图谱还原（读 e2e/plans/README）
2. 启动应用实测走查（含记录截图与日志）
3. 汇总评分与断点清单
4. 写报告 + 生成 PDF

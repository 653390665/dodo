# InkFlow 墨影 产品体验审计：功能、体验与链路顺畅度

> 研究时间：2026-09-03 | 审计对象：InkFlow 墨影 v1.2.0（dev 模式实测）| 方法：横纵分析法 · 实测走查

## 一、审计结论（TL;DR）

**设计上的产品链路是完整的，但真实模型下的第一步 AI 交互就被一个兼容性缺陷阻断。**用 e2e 测试的确定性夹具跑，全旅程（开书→生成→审校→导出）都能走通；换上真实的 DeepSeek V4 Flash 模型，"开书立项"这一步连续失败两次，且失败后用户输入被清空。这是"功能跑通"与"真实可用"之间的核心差距。此外实测确认了两个体验断点（失败后状态回退、空状态循环指引）和两个疑似缺陷（字数统计不更新、自动保存未触发）。

## 二、审计范围与方法

- **静态图谱**：从 `tests/e2e/core-flow.spec.ts`（含"full novel happy path"）、`full-browser-click-journey.spec.ts`、README 工作流图、plans/ 审计记录反推设计旅程。
- **动态走查**：以隔离数据目录（`INKFLOW_CONFIG_DIR` 指向临时目录，不触碰真实数据）启动 dev 服务，用真实浏览器以"新作者第一次使用"视角走查全部主链路，服务端日志交叉验证。
- **模型配置**：DeepSeek V4 Flash（`https://api.deepseek.com/v1`），连接测试通过（发现 3 个模型）。

## 三、链路走查结果与评分

| 链路 | 评分 | 结果 |
|---|---|---|
| 首启与引导 | 4.5 / 5 | ✅ 优秀 |
| BYOK 模型配置 | 3.5 / 5 | ✅ 可走通，有摩擦 |
| 开书立项（真实模型） | **1.5 / 5** | ❌ P1 阻断 |
| 本地建书与编辑器 | 3.5 / 5 | ⚠️ 可用，疑似缺陷 |
| 正文导出 | 4 / 5 | ✅ 触发成功 |
| 导航与空状态 | 4 / 5 | ✅ 良好，一处循环指引 |

### 3.1 首启与引导（4.5 / 5）——产品的门面担当

首屏同时呈现四层信息且互不打架：左侧"AI 创作状态监视器"（AI 引擎连接、语义索引、数据保护三项诚实标注，语义索引明确写"不可用（不影响保存）"）；琥珀色"本地无缝降级指引"横幅；"新手启航指南"弹条（说清书库为空、两条起步路径、去哪里配 API Key）；三步开书向导（题材→平台→篇幅文风）完整展开，未完成的步骤按钮呈禁用态。

对照竞品基准：NovelCrafter/Sudowrite 的首启都要用户先读文档才能找到 Key 配置入口，InkFlow 把"状态诚实 + 下一步指引"做在了首屏，这是实测中体验最好的部分。扣 0.5 分的原因见 4.2 的占位符问题。

### 3.2 BYOK 模型配置（3.5 / 5）——能走通，但踩了两脚

正向：设置弹窗分区明确（"默认只处理模型接入；提示词实验室适合需要精修 AI 行为时再进入"）；"生效验证链"三步说明；质量守卫三档（严格纠错/前置规则/关闭守卫）把成本与质量的选择权交给用户；"测试连接"成功后会列出发现的模型数。

实测踩到的两脚：
1. **Base URL 留空时，报错是英文 "Validation failed"**，中文排查建议只泛泛说"检查 Base URL 格式"，不指明"该字段为空"。用户在三栏里猜哪个错了。
2. **全新安装时 API Key 输入框的占位符就是"已配置；留空保留，输入新 Key 替换"**——首启并未配置任何 Key，这个占位符会让用户以为已经配置好了。

### 3.3 开书立项（1.5 / 5）——P1 阻断，本次审计最重要发现

三步向导本身流畅（题材/平台/篇幅/文风全是可视化卡片选择，"番茄平台=黄金三章爆发"这类文案把平台规则翻译成了创作语言，是好的产品设计）。点击"唤醒灵感，智能开书立项"后，真实模型下**连续两次失败**：

- 第一次：`模型输出未通过质量校验，请重试`
- 第二次：`模型服务返回空结果`

**根因已定位到代码**（`server/lib/server-llm.ts`）：应用对 OpenAI 兼容渠道硬性封顶 `max_completion_tokens = min(maxTokens, 2048)`。DeepSeek V4 Flash 是推理模型，响应含 `reasoning_content`——复杂立项提示词下推理就耗尽了 2048 token 预算，`content` 返回为空（第二次错误的来源）；偶尔挤出的部分内容又被严格质量守卫拒绝（第一次错误的来源）。代码里其实已经有 `reasoning_only`、`length_exhausted` 的错误分类（说明作者预见过这类模型），但 2048 上限没有为推理模型留出预算。**作者自己最常用的就是 DeepSeek——这个兼容性问题会打在最常用的模型上。**

更糟的是失败之后的表现：**向导回退到第一步，灵感输入框被清空**，立项按钮回到禁用态。用户写下的创意 seed 直接丢失，必须完整重填。对创作工具来说，"用户输入的创意文本"是最不该丢的东西。

### 3.4 本地建书与编辑器（3.5 / 5）

"创建空白作品"绕过 AI 直接建书成功，验证了"本地无缝降级"的承诺。编辑器信息密度出色：写法来源面板（作品默认/本章/技法/系统护栏 12 条）、空章节指引（"当前阶段主动作：生成分镜，也可以直接在编辑器中起笔"）、"索引 降级"诚实标记、导出入口。

**疑似缺陷（P1，建议人工复验）**：在正文 textarea（占位符"在这里开始书写这一章……"）输入 43 字后——包括用 `execCommand insertText` 的真实输入路径复测——顶部"字数 0"始终不更新，且 10 秒以上未见自动保存触发（产品宣称 3 秒防抖自动保存）。e2e 用 Playwright `fill()` 填充后只断言了 textarea 的 value 和导出成功，**没有断言字数统计和保存指示器**，所以这个缺陷从测试网里漏了过去。保留意见：审计环境跳过了"选择推荐创作流程"模态（实测未出现），不排除该模态承担了编辑器状态初始化的职责；需要按 e2e 的完整路径人工复验。

### 3.5 导出与导航（4 / 5）

导出按钮触发 PDF 导出模块执行成功。导航走查：我的书库空状态干净（两条创建路径）；创作工作台的"暂未开启"预览态把四象限价值讲清楚了；资料续写页用 4 步说清了"这不是资料管理页"的定位。两个小问题：① 书库空状态引导"去智能管家构思故事框架"，但智能管家页在无作品时显示的是工作台占位（"先选择或创建作品"）——**循环指引**，新用户被绕回原地；② 侧边栏"高级工具"点击后落在"资料续写"页，指向与命名不符。

## 四、断点清单（按优先级）

| # | 严重度 | 位置 | 现象 | 修复建议 |
|---|---|---|---|---|
| 1 | **P1** | server-llm.ts L278 | 推理模型（V4 Flash）被 2048 token 上限掐断，立项/生成必失败 | 按模型是否为推理型动态放宽 max_completion_tokens（DeepSeek 官方支持 8k+），或对 reasoning_content 单独预算 |
| 2 | **P1** | 开书向导 | 立项失败后回退第一步、灵感文本清空 | 失败保留全部向导状态与输入，就地提供"重试" |
| 3 | **P1(疑似)** | 编辑器 | 手写 43 字后字数统计 0、自动保存未触发 | 先人工复验；若确认，检查 onChange → store 的绑定 |
| 4 | P2 | 设置弹窗 | Base URL 为空时错误文案是英文 Validation failed，未指明字段 | 校验错误映射为中文字段级提示 |
| 5 | P2 | 设置弹窗 | 全新安装时 Key 占位符显示"已配置" | 按真实配置态切换占位符 |
| 6 | P2 | 书库/管家空状态 | "去智能管家构思"→管家页要求"先创建作品"循环指引 | 无作品时智能管家应提供独立的构思入口 |
| 7 | P3 | 侧边栏 | "高级工具"落在"资料续写"页 | 核对导航指向 |
| 8 | P3 | 设置弹窗 | 弹窗对失焦/标签切换敏感（自动化环境观察，疑似） | 复验是否误关 |

## 五、功能完成度地图（README 宣称 vs 实测）

| README 宣称 | 实测 |
|---|---|
| 一句话开书（智能立项） | ❌ 真实模型下阻断（#1） |
| 本地无缝降级写作 | ✅ 兑现（建书/编辑/导出全程无 AI 可用） |
| 状态诚实展示 | ✅ 兑现（监视器/索引降级横幅） |
| 设定记忆/记忆雷达 | ⏳ 未实测（依赖生成链路，被 #1 阻断） |
| 去AI味审稿 | ⏳ 未实测（同上）；守卫三档 UI 已就绪 |
| 3 秒防抖自动保存 + 实时字数 | ⚠️ 疑似失效（#3） |
| 导出 | ✅ 兑现 |

## 六、给下一步的建议

1. **先修 #1**：这是所有 AI 链路的总闸门。修好后立项、分镜、正文、审校四条链路可能一并恢复——建议同时把"推理模型 max_tokens"加进 e2e 的真实模型冒烟用例（现有 fixture 测不出这类问题）。
2. **再修 #2 和 #3**：用户输入丢失和数据保存是创作工具的信任底线。
3. 体验层面，这个产品的"诚实降级"设计（状态监视器 + 琥珀横幅 + 本地可写）是竞品（Sudowrite/NovelCrafter 均为纯云端）没有的差异化资产，值得作为产品叙事保持下去。

## 勘误与修复记录（2026-09-03 修复后补充）

本报告的断点清单经代码级复查后，做如下勘误与状态更新：

| # | 原判定 | 勘误/状态 |
|---|---|---|
| 1 (P1) | "server-llm.ts 对所有渠道封顶 2048" | **根因修正**：2048 封顶仅作用于 MiniMax 渠道。真因是 onboarding.ts 的 story-cards 调用自身传 maxTokens:2048 且漏传 disableThinking（仓库其他推理重调用均有）。已修复：`disableThinking: true` + `maxTokens: 4096` + `outputMode: 'audit-json'`（立项卡是 JSON 数据，prose 质量守卫会把 JSON 字段误判为"对白突兀"） |
| 2 (P1) | "向导回退第一步且灵感清空" | **重新定性**：POST 成功后清空输入是设计行为；模型失败时 hook 刻意保留 fallback 卡片并显示警告。真问题是模型路径必败（#1），已随 #1 修复 |
| 3 (P1) | "字数统计 0、自动保存未触发" | **根因确认并修复**：WritingSurface 的 300ms 防抖提交走 handleUpdateContent，但该函数更新 store 时只写 content 不重算 wordCount，而字数指示器读 store 的 currentChapter.wordCount。已补 wordCount 同步（useEditorPersistence.ts 两处） |
| 4 (P2) | 设置弹窗英文报错 | **已修复**：SettingsModal 消费 400 响应的 details 字段，映射为中文字段级提示（Base URL：格式无效…） |
| 5 (P2) | Key 占位符"已配置"误导 | **降级为待复验**：代码逻辑正确（hasApiKey 驱动），审计环境观察到的现象可能与 secure-key 残留有关 |
| 6 (P2) | 书库→管家循环指引 | **已修复**：空状态文案改为与现有按钮一致，移除未兑现的智能管家指引 |
| 7 (P3) | "高级工具落在资料续写页" | **误报撤回**：高级工具本就是手风琴折叠器（Sidebar.tsx:141），审计时误触相邻按钮 |
| 8 (P3) | 弹窗对失焦敏感 | 待复验（自动化环境观察） |

**端到端回归结果**（2026-09-03，隔离环境 + 真实 DeepSeek V4 Flash）：立项链路修复前两次失败（空结果/质量校验拒绝），修复后 story-cards job `completed`，3 张 AI 卡返回，UI 显示"模型版已返回，已自动替换本地保底草案"。新增测试：DeepSeek 渠道 thinking 禁用与 max_tokens 透传断言（tests/server-llm.test.ts，22 pass）；editor-persistence 14 pass；typecheck 通过。

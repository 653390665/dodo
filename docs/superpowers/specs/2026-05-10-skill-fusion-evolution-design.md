# InkFlow Skill 融合与进化设计

## 1. 目标

本设计解决的不是“Skill 能否保存为新版本”这种基础问题，而是：

- Skill 如何真正吸收彼此优点，而不是简单拼接
- 用户如何显式地做融合实验
- 系统如何基于长期反馈，逐渐学会推荐更有效的融合方向

核心目标是把 Skill 从“可编辑卡片”推进成“可炼成、可迭代、可被验证的写作能力资产”。

## 2. 当前状态与缺口

现有设计已经覆盖：

- 技能仓库详情、编辑、保存为新版本
- 版本谱系
- 试驾对比台
- 维度标签与组合画像
- 使用反馈与权重优化

但“融合”仍然停留在框架词，缺少明确的产品定义：

- 融合是在什么场景下发生
- 融合到底保留什么、吸收什么
- 融合后的产物属于谁的 lineage
- 系统何时建议融合，何时不该提示

所以这一轮设计只补一件事：

**让 Skill 融合从概念变成一个可操作、可解释、可试驾的工作流。**

## 3. 设计结论

采用 `长期混合型 + 第一阶段显式融合优先` 的方案。

### 3.1 长期路线

Skill 进化分两条路：

1. `显式融合`
   - 用户主动选择两张或多张 Skill 进行融合
   - 系统生成一张新的候选 Skill

2. `隐式进化`
   - 系统根据长期使用反馈和项目偏好，逐步调整推荐优先级、适配解释和融合建议

### 3.2 第一阶段重点

第一阶段只做：

- `1 主卡 + 1 辅卡 -> 1 张新 Skill 候选`
- 用户手动发起
- 系统给出融合说明
- 先试驾、后保存

第一阶段不做：

- 自动直接改写 Skill 内容
- 多卡同时融合
- 黑箱式自动炼成

## 4. 为什么先做显式融合

如果一开始就做自动进化，问题很明显：

- 用户不知道系统改了什么
- 容易不信任
- 出错时也很难回溯

显式融合的优点是：

- 用户主动发起，意图明确
- 融合关系可见
- 结果可试驾、可放弃
- 更容易形成版本谱系和对比过程

所以第一阶段应当让用户先理解：

**“系统是如何吸收优点的。”**

然后再进入长期自动优化。

## 5. 融合的本质定义

Skill 融合不应被理解成“把两张卡的文本字段拼起来”，而应定义为：

**在保持主卡身份清晰的前提下，吸收辅卡的优势特征，生成一个新的可试驾版本。**

这意味着：

- 主卡决定新卡的核心身份
- 辅卡提供定向增强
- 新卡仍然必须有清晰主维度

融合的关键不是“平均混合”，而是：

**主卡保身份，辅卡给增强。**

## 6. 第一阶段融合模型

### 6.1 基本形式

采用：

`1 主卡 + 1 辅卡 -> 1 张新版本 Skill`

### 6.2 主卡职责

主卡决定：

- 新卡的主维度
- 新卡的核心身份
- 新卡主要继承的文风 / 角色 / 世界 / 节奏基线
- 版本谱系的主 lineage 归属

### 6.3 辅卡职责

辅卡提供：

- 某些次维度优势
- 可迁移的写法能力
- 对当前项目更有价值的补强点

例如：

- 人物对峙张力
- 更克制的解释方式
- 更强的剧情推进
- 更稳定的节奏节拍

### 6.4 融合结果

融合产物不是直接覆盖原卡，而是：

- 一张新的候选 Skill
- 带新的版本号或新的分支 lineage
- 默认进入试驾对比
- 用户确认后才正式保存

## 7. 吸收什么，不吸收什么

### 7.1 建议允许吸收的内容

- 文风倾向
- 句法特征
- 人物对话方式
- 冲突推进模式
- 节奏控制倾向
- 伏笔布置手法

这些都属于“写法能力”。

### 7.2 不建议直接吸收的内容

- 具体作品设定
- 专属名词
- 具体人物背景
- 特定题材外壳
- 强上下文依赖内容

这些属于“原作残片”，不是可复用能力。

所以融合系统必须吸收的是：

**能力，不是内容残渣。**

## 8. 用户如何理解融合结果

融合后不能只给一张新卡，还必须给一份简洁的融合说明。

建议固定成 4 块：

### 8.1 主卡身份

回答：

- 这张新卡主要继承谁
- 它本质上仍然是什么类型的 Skill

### 8.2 吸收优点

回答：

- 从辅卡拿到了什么增强
- 是增强文风、人物、冲突、节奏还是世界表达

### 8.3 适合场景

回答：

- 更适合什么类型章节
- 更适合什么项目倾向

### 8.4 潜在风险

回答：

- 可能压掉什么
- 哪些维度会产生冲突
- 再叠什么类型的卡容易失控

这一步是建立信任的核心。

## 9. 融合发生在哪里

推荐采用 `两段式融合`。

### 9.1 创作舞台负责发现机会

在装配区或推荐反馈区，系统只做：

- 提示两张卡长期共同使用稳定
- 说明为什么值得融合
- 建议谁做主卡、谁做辅卡

这里不做重操作。

### 9.2 技能仓库负责完成融合

真正的融合、试驾、保存动作应在 `技能仓库` 或其子视图 `融合工坊` 中完成。

原因：

- 融合本质上是资产演化
- 需要版本谱系和试驾承接
- 不应把创作现场做得过重

所以：

- 创作舞台负责发现
- 技能仓库负责炼成

## 10. 第一阶段交互流程

### A. 创作舞台提示融合机会

当系统发现以下条件同时成立时，给出提示：

- 两张卡在同一项目中被反复共同使用
- fit score 长期稳定不低
- 用户没有频繁替换掉其中一张
- 两张卡主维度不完全冲突
- 当前项目画像显示它们都贴近偏好

提示内容包括：

- 为什么建议融合
- 哪张更适合做主卡
- 预期会吸收什么优点

### B. 点击进入融合工坊

进入技能仓库内的融合工坊后，只做四件事：

1. 选定主卡
2. 选定辅卡
3. 查看融合说明
4. 一键试驾 / 保存为新版本

### C. 默认先试驾

融合结果默认不是“已生效”，而是“候选版本”。

用户需要先看：

- 试驾结果
- 融合说明
- 对比当前版本差异

确认后再保存。

## 11. 自动进化第一阶段做什么

第一阶段自动进化不直接改卡内容。

它只做三件事：

1. 调整推荐优先级
2. 调整适配分解释
3. 给出“建议融合”的提示

也就是说，自动进化第一阶段更像：

**融合建议器**

而不是：

**自动改卡器**

## 12. 与偏好飞轮的关系

融合系统不应孤立工作，而要读取项目偏好画像。

融合建议应当考虑：

- 当前项目更偏哪类维度
- 哪些类型 Skill 更常被接受
- 哪些组合经常被保留
- 哪些冲突经常被打回

这样融合提示才真正像：

**“更贴近当前作品的写法演化建议”**

而不是通用炼卡系统。

## 13. 第一阶段范围

第一阶段只做：

1. `1 主卡 + 1 辅卡` 的显式融合
2. 创作舞台中的融合建议提示
3. 技能仓库中的融合工坊
4. 融合说明
5. 先试驾后保存

第一阶段不做：

- 多卡融合
- 自动直接改写 Skill 文本
- 全自动融合批处理
- 复杂的进化趋势图

## 14. 成功标准

如果这套设计做对，用户应当明确感知到：

1. Skill 不只是可编辑，还能被炼成更强的新版本
2. 融合不是拼接文本，而是在吸收优点
3. 每次融合都能说清楚保留了什么、吸收了什么、风险是什么
4. 创作现场能感知到“该不该融合”
5. Skill 仓库真正成为写法资产进化场

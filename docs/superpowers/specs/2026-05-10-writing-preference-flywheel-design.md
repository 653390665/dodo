# InkFlow 写法偏好飞轮与进化感知设计

## 1. 目标

本设计解决的不是“Skill 分数怎么算”本身，而是：

- 用户如何感知系统越来越懂自己
- Skill 的评分、融合、反馈如何长成“我的写法”
- 什么偏好应该只停留在当前项目，什么偏好才值得进入长期画像

核心目标是把 InkFlow 从“功能很强的 AI 写作器”推进到“会陪用户长出个人写法系统”的产品。

## 2. 设计结论

采用两段式感知路径：

1. **先做即时反馈**
   - 先告诉用户：`这次为什么更适合你`
   - 场景主要发生在 Skill 装配、替换、融合、生成后回看

2. **再沉淀长期画像**
   - 再告诉用户：`这本书的写法正在形成什么样子`
   - 等项目内积累足够行为数据后，再展示项目级画像

长期全局画像不是第一层，而是最后沉淀层。

## 3. 为什么不能只展示评分

现有的 Skill 评分或 fit score 可以作为底层信号，但它本身不足以形成用户感知。

如果界面只显示：

- 72 分
- 81 分
- 88 分

用户并不知道：

- 为什么涨了
- 涨的是哪部分
- 这次变化和“我”的关系是什么

所以评分只能作为证据，而不是体验本身。

用户真正需要感知的是：

1. `这次组合更适合我了`
2. `系统知道我偏爱什么`
3. `为什么它建议这样配，而不是那样配`

## 4. 三层偏好飞轮

### 4.1 会话层

服务当前一轮灵感碰撞或当前一段创作。

记录内容：

- 当前更偏冷峻还是热烈
- 当前更重人物冲突还是世界设定
- 当前更想快推进还是慢铺陈
- 当前对某些 Skill 的即时接受或排斥

特点：

- 临时
- 噪声高
- 不进入长期作者画像

会话层的作用是让 agent 在这一轮对话中快速纠偏，而不是立刻学习“用户本人是什么样的作者”。

### 4.2 项目层

这是最关键的一层。

当某种偏好在**同一部作品**里反复出现，系统就把它沉淀成项目级偏好画像。

项目层的作用：

- 影响当前作品的 Skill 推荐
- 影响 Skill 适配评分
- 影响融合后的解释文案
- 影响设定补全建议
- 影响创作舞台中的协作副驾建议

它代表的是：

**“这本书正在形成的写法”**

而不是：

**“这个用户的一生偏好”**

### 4.3 全局作者层

只有当某种倾向在**多个项目、多次交互**中都稳定出现，才升级到 `user.md`。

这一层只沉淀：

- 跨项目稳定成立的作者偏好
- 对长期推荐有价值的倾向
- 用户没有持续反对的偏好

它不应该收录：

- 某一本书的特殊题材需求
- 某次灵感碰撞里的临时口味
- 用户一时试验性的偏好

所以：

- `session` 是即时协作层
- `project` 是当前作品学习层
- `user.md` 是长期稳定沉淀层

## 5. 项目偏好画像结构

项目层采用**中等结构型画像**，不做成过重的分析后台，也不只是几个模糊标签。

### 5.1 高层偏好标签

用于用户快速理解“这本书的当前写法倾向”。

建议包含：

- 冷峻 / 热烈
- 紧推进 / 慢铺陈
- 强冲突 / 轻冲突
- 重人物 / 重世界

这些标签不追求学术准确，追求用户能一眼读懂。

### 5.2 维度权重

用于支撑评分、推荐、融合和解释。

建议记录：

- `styleWeight`
- `characterWeight`
- `worldWeight`
- `plotWeight`
- `pacingWeight`

这些不是直接给用户编辑的底层参数，而是系统用来解释“为什么更适合你”的依据。

### 5.3 Skill 行为偏好

记录真实使用行为，而不是只看显式设置。

建议记录：

- 常接受的 Skill 维度
- 常拒绝的 Skill 维度
- 高频保留的组合
- 高频替换掉的组合

这部分直接影响后续：

- 推荐哪类卡
- 少推荐哪类卡
- 哪些融合更容易被接受

### 5.4 解释性备注

这是让画像更像“写法系统”而不是“冷数据面板”的关键。

建议沉淀成简短自然语言：

- 本项目更接受压迫感强的短句
- 不喜欢过度抒情和解释性文字
- 更偏人物对峙，不希望世界设定抢戏
- 喜欢高冲突、快推进，但不接受纯爽点堆砌

解释性备注不要求每次都更新，但在偏好明显变化时应同步刷新。

## 6. 升级到 user.md 的规则

### 6.1 不直接写入

在灵感碰撞初期，agent 不应该频繁改 `user.md`。

原因：

- 前期表达具有试探性
- 容易把项目偏好误写成作者长期偏好
- 一旦写偏，后面所有推荐都会受污染

### 6.2 推荐升级路径

采用严格升级链：

1. `会话层`
2. `项目层`
3. `全局作者层 / user.md`

### 6.3 项目层形成条件

某种偏好应当至少满足以下条件才升级到项目层：

- 在同一项目中反复出现
- 连续多次被用户接受或强化
- 没有被用户明显否定

推荐最低规则：

- 同类倾向出现至少 3 次

### 6.4 写入 user.md 的条件

某种偏好应当至少满足以下条件才进入 `user.md`：

- 跨 2 个及以上项目持续出现
- 同类倾向稳定成立
- 用户没有频繁把它纠正掉
- 它对长期推荐有明确价值

也就是说，`user.md` 的写入门槛要明显高于项目层。

## 7. 用户如何感知这套进化

### 7.1 第一层：装配区即时反馈

用户在 Skill 装配、替换、融合时，应该立刻看到：

- 这次适配分为什么变高或变低
- 哪些维度更贴近当前项目偏好
- 哪些冲突被消掉了

这里回答的是：

**“为什么这次更适合我。”**

推荐反馈示例：

- 这次组合比上次更贴近你在本项目中的偏好：冷峻、强冲突、紧推进
- 提升主要来自：文风统一、人物对峙更强、节奏冲突减少
- 当前主要拖分项：世界铺陈偏重，压低了人物推进效率

### 7.2 第二层：生成后结果反馈

在正文生成、审计或局部精修之后，再补一层结果反馈：

- 这次组合是否真的带来了更好的接受度
- 用户是否保留了结果
- 哪类 Skill 被保留或被替换

这里回答的是：

**“预期适配是否真的兑现了。”**

### 7.3 第三层：项目画像面板

当项目内积累到一定行为数据后，再出现一个简洁的“项目写法画像”面板。

它的职责不是解释每一轮，而是总结：

- 当前项目写法倾向
- 最近在往什么方向收敛
- 哪类 Skill 更容易被接受
- 哪类组合经常被打回

这里回答的是：

**“这本书的写法正在形成什么样子。”**

## 8. 用户干预机制

这套飞轮必须允许用户纠偏，否则它只是一个自说自话的黑箱推荐系统。

推荐只给 3 个轻量干预动作：

1. `这更像我`
2. `这不是我想要的`
3. `仅限本项目`

这 3 个动作已经足够影响：

- 项目层权重
- 是否允许升级到全局
- 某些推荐维度的优先级

它们比复杂设置页更轻，也更符合真实创作过程中的协作节奏。

## 9. 与现有系统的联动关系

### 9.1 与 Skill 评分联动

现有评分系统不废弃，而是升级为：

- 基础适配分
- 偏好贴合分
- 冲突惩罚分
- 历史接受度修正

最终给用户看到的不是“一个神秘总分”，而是：

- 总分变化
- 变化原因
- 与当前项目偏好的关系

### 9.2 与 Skill 融合联动

融合后的 Skill 不只看能力是否更强，还要看：

- 是否更贴近当前项目偏好
- 是否减少了用户经常排斥的冲突项

这样“融合提升”才会被用户感知成：

**“更像我了”**

而不是：

**“系统又算出了一个新分数”**

### 9.3 与推荐系统联动

推荐逻辑应当逐步从“通用推荐”进化到：

- 基于故事方案卡的初始推荐
- 基于项目画像的持续推荐
- 基于全局作者层的长期微调

这三层不能一开始混成一个黑箱。

## 10. 第一阶段范围

第一阶段只做：

1. Skill 装配区即时反馈
2. 评分变化解释
3. 项目层轻量画像
4. 3 个轻量纠偏动作

第一阶段不做：

- 完整的全局画像管理后台
- 自动频繁改写 `user.md`
- 复杂趋势图表
- 多项目高级统计分析面板

## 11. 成功标准

如果这套设计做对，用户应当能明确感知到：

1. 系统不是只会给一个分数
2. 系统能解释为什么这次组合更适合当前项目
3. 系统会逐渐学会这本书的写法偏好
4. 用户能纠正系统，而不是被系统定义
5. 长期来看，InkFlow 在形成“我的写法系统”，而不是只提供一次性 AI 输出
